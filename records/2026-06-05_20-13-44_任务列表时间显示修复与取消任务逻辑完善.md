## [1] 修复任务列表页面时间显示规范化

### 问题描述

任务列表页面（frontend/pages/tasks.html）中，`formatDuration` 函数格式化时间时，未对浮点数秒值进行截断处理。当传入 `162.379999999999995` 这样的浮点数时，会显示为 `2分42.379999999999995秒`，用户体验极差。

### 根因分析

`formatDuration` 函数有三处导致浮点小数显示的问题：

1. **第925行**：`seconds < 60` 时直接返回 `${seconds}秒`，未截断
2. **第928行**：`const secs = seconds % 60` — JavaScript 浮点数取模产生非整数余数（IEEE 754 精度问题）
3. **第929行**：`${mins}分${secs}秒` 直接使用浮点余数

**浮点数来源**：
- 后端 `ModelState.total_execution_time` 通过 `round(x, 2)` 处理后仍为浮点数
- `task.wait_time_seconds` 和 `task.execution_time_seconds` 可能是浮点数

### 修复方案

在 `formatDuration` 函数开头添加 `seconds = Math.floor(seconds)`，将所有后续计算基于整数秒值：

```javascript
function formatDuration(seconds) {
    if (!seconds || seconds < 0) return '0秒';
    seconds = Math.floor(seconds);  // 截断为整数，避免出现浮点小数
    // ... 其余逻辑不变
}
```

- `frontend/pages/tasks.html` — 第923-934行，formatDuration 函数

## [2] 修复排队中任务的取消逻辑

### 问题描述

任务队列中，排队（queued）状态的任务虽然有取消按钮，但取消逻辑存在两个缺陷：

1. **dispatch 循环中的死代码**：任务在设置 `PROCESSING` 状态后才检查 `CANCELLED`，导致取消检查永远不会触发
2. **取消与派发的竞态窗口**：任务从 `_pending_list` 弹出后、设置为 `PROCESSING` 前，存在一个时间窗口。此时用户点击取消，`cancel_task` 能成功设置状态为 `CANCELLED`，但 dispatch 循环中的检查是死代码，任务仍会继续执行

### 根因分析

原代码逻辑：

```python
# 步骤1: 将所有任务标记为 PROCESSING（覆盖了可能的 CANCELLED 状态）
for task in tasks_to_dispatch:
    task.status = TaskStatus.PROCESSING.value  # ← 问题：直接覆盖

# 步骤2: 检查 CANCELLED（死代码！步骤1已经改为 PROCESSING）
for task in tasks_to_dispatch:
    if task.status == TaskStatus.CANCELLED.value:  # ← 永远不会为真
        ...  # 跳过已取消任务
        continue
    asyncio.create_task(self._execute_task(task))
```

### 修复方案

**修复1**：dispatch 循环中，先过滤已取消任务，再设置 `PROCESSING` 状态：

```python
# 步骤1: 从 self.tasks 重新读取状态，过滤已取消任务
valid_tasks = []
for task in tasks_to_dispatch:
    current = self.tasks.get(task.task_id)
    if current and current.status == TaskStatus.CANCELLED.value:
        system_logger.info(f"【任务队列】跳过已取消任务: {task.task_id}")
        continue
    valid_tasks.append(task)

# 步骤2: 仅对有效任务设置 PROCESSING 状态
for task in valid_tasks:
    task.status = TaskStatus.PROCESSING.value
    ...

# 步骤3: 派发执行
for task in valid_tasks:
    asyncio.create_task(self._execute_task(task))
```

**修复2**：`_execute_task` 开头增加取消检查，作为兜底保护：

```python
async def _execute_task(self, task: TaskRecord):
    # 检查任务是否已被取消（在dispatch和execute之间可能被取消）
    current = self.tasks.get(task.task_id)
    if current and current.status == TaskStatus.CANCELLED.value:
        system_logger.info(f"【任务队列】任务已被取消，跳过执行: {task.task_id}")
        # 清理 processing_tasks 和模型状态
        ...
        return
    # ... 继续执行
```

### 取消流程（修复后）

```
用户点击取消按钮
    ↓
POST /tasks/{task_id}/cancel
    ↓
cancel_task() 检查状态 → 仅 queued 状态可取消
    ↓
从 _pending_list 移除 → 设置状态为 CANCELLED → 保存
    ↓
dispatch 循环: 从 self.tasks 重新读取状态 → 发现 CANCELLED → 跳过
    ↓
（兜底）_execute_task: 再次检查状态 → 发现 CANCELLED → 跳过
```
